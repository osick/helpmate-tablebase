# Table contribution pipeline — design

Date: 2026-09-30. Status: awaiting review.

## Why

Two outside contributors have delivered 29 six-piece tables so far (T31M: KRB, HF
PR #1, merged in v0.20.0; popeye37: KRR, HF PRs #2–#15, open), and three more
claims are running (#40 KQvk???, #45 KRNvk??, KRRvkpp handed to T31M). Everything
between "claim" and "credited" is currently done by hand: claims are free text,
contributors keep status emoji lists in the issue body, nothing links an HF PR
to its claim, `tools/verify_corpus.py` is the only verification script (block
integrity only), the manifest was regenerated by hand, and the corpus counts in
four documents were edited by hand in the release commit.

Goal: a contribution goes from claim to credited with the maintainer doing two
things — reading a verification report and running one `accept` command.

## Agreed decisions

- Claims live on GitHub, data PRs on Hugging Face (as today).
- Verification is run by the maintainer on the local box (it needs the 55+ GiB
  corpus as sub-tables; a free CI runner cannot hold it). It posts its report
  automatically.
- **Merge happens on an explicit `accept`, never automatically on a green
  verification** (user decision, 2026-09-30). The maintainer vouches for the data.
- Contributors are **not** added as GitHub collaborators (that grants write
  access to the code). Credit is: `docs/MATERIALS.md`, the README/dataset-card
  contributor tables, an `.all-contributorsrc` entry of type `data`, and a
  `Co-authored-by:` trailer on the docs commit.
- Data additions do **not** bump VERSION. They get a `### Data` entry under
  `## [Unreleased]` in CHANGELOG.md and ride along with the next code release.
- DEEPEST / site data / booklet regeneration stays a separate, batched manual
  step (it takes ~80 minutes of mining); `contrib status` reports how many tables
  arrived since the last refresh.

## Terms

- **Material universe**: every material with 3–6 pieces including both kings,
  White and Black pieces each in canonical order Q R B N P
  (`KRBvkqq`, `KBBPvk`). Counts: 3 → 10, 4 → 55, 5 → 220, 6 → 715; **1000 in
  total**. A material whose White side is a bare king is a **marker** (no
  helpmate possible; the generator writes a v2 marker table): 70 of the 715
  six-piece materials, so 645 need a real table.
- **Status** of a material, derived, never typed by hand, in precedence order:
  `done` (in the HF manifest) → `in review` (in an open HF PR) → `claimed`
  (named by an open GitHub claim issue) → `open`.

## Components

### 1. `tools/materials.py` — the universe (stdlib only)

`universe() -> list[Material]` with `name`, `pieces`, `pawns`, `marker`;
`canonical(name) -> str | None` (normalises order, rejects non-materials);
`expand(pattern) -> list[str]` for wildcard patterns, where `?` matches one
non-king piece of that colour (`KQvk???` → every canonical `KQvk` + three black
pieces, deduplicated after canonicalisation). One place to answer "is this a
material" for every other component.

### 2. `data/contributions.json` — the one hand-owned record

Committed; written only by `contrib accept` (and by hand for corrections).

```json
{
  "schema": 1,
  "contributors": {
    "T31M":     {"github": "T31M", "hf": "T31M", "display": "T31M", "anonymous": false},
    "popeye37": {"github": "popeye37", "hf": "popeye37", "display": "popeye37", "anonymous": false}
  },
  "tables": {
    "KRBvkqq": {"contributor": "T31M", "hf_pr": 1, "claim": 41, "merged": "2026-09-26",
                "generator_version": "0.19.0",
                "verification": {"tool": "contrib 1", "head": "<hf pr head sha>",
                                 "date": "...", "samples": 4000, "result": "pass"}}
  }
}
```

Materials not in `tables` but in the manifest were computed by the maintainer.
Seeded with T31M's 15 tables (verification `null`: accepted before this tool
existed — shown as "reviewed" not "verified").

### 3. Claim issue form + `claims.yml` workflow (GitHub Actions, no secrets)

- `.github/ISSUE_TEMPLATE/claim.yml`: title `claim: <summary>`; fields:
  materials (one name or wildcard pattern per line), Hugging Face username,
  credit name, "do not name me" checkbox, hardware (optional). Adds label `claim`.
- `tools/contrib_claims.py` (stdlib + `urllib`; reads the public HF API
  anonymously: `manifest.json` at `main` and the list of open PRs with their
  files) runs on `issues: [opened, edited, reopened]`, `issue_comment`, a daily
  schedule, and `workflow_dispatch`. For each open `claim` issue:
  - parse every canonical material name or wildcard pattern anywhere in the body
    (so the existing free-text claims #39, #40, #45 parse unchanged); a name
    struck through (`~~KRRvkpp~~`) is released, which is how a handover is
    recorded;
  - maintain **one** bot comment (found by a hidden `<!-- contrib-status -->`
    marker and edited in place) with a per-material table: done / in review
    (HF PR #n) / claimed, plus a line telling the contributor they no longer need
    to maintain status emoji by hand;
  - label `claim-conflict` and say so when a material is already done, in
    review by someone else, or claimed in another open issue (first claim wins;
    the maintainer resolves handovers like KRRvkpp by editing the issues);
  - label `claim-stale` after 21 days without activity by the author. It never
    closes an issue — lapsing a claim is the maintainer's call.
- Permissions: `issues: write`, `contents: read`. It commits nothing, so branch
  protection and the "PRs created by GITHUB_TOKEN don't trigger CI" problem
  never arise.

### 4. `helpmate-tables push --create-pr --claim N [--github LOGIN]`

Adds a machine-readable description to the HF PR:
`Claim: osick/helpmate-tablebase#N` and `GitHub: @LOGIN`. This closes the
identity gap from the contributor's side; `open_pr` gains a `description`
argument. Without `--claim` the behaviour is unchanged (PRs from older clients
still work — see identity resolution in `accept`).

### 5. `tools/contrib.py` — the maintainer's CLI

All HF and GitHub calls go through an injectable client (the `hub_factory`
pattern of `tables_cli.py`) so the command logic is tested against fakes.

**`contrib status`** — one table joining open HF PRs ↔ claim issues ↔
last verification result ↔ accepted, plus "N tables since the last DEEPEST
refresh". Read-only.

**`contrib verify PR [PR ...] [--samples N] [--no-post] [--yes]`**

1. *Plan*: list the PR's files and sizes at `refs/pr/N`, check free disk space,
   print the download size and ask for confirmation unless `--yes`
   (house rule: no large download unannounced).
2. *Download* into `~/tb-staging/pr-N/`, then build an overlay directory
   `~/tb-staging/pr-N/overlay/` of symlinks: every file of the local corpus
   (`--tables`, default `~/tb`) plus the PR's files, so sub-table probes work.
3. *Checks*, cheapest first; each yields pass / fail / warn with evidence:
   - **V1 PR hygiene** — only `<M>.hm` + `<M>.stats.json` pairs; every `M`
     canonical; not already in the manifest (if it is and sha256 differs: fail
     with both hashes); claim link present (warn if missing).
   - **V2 header** — magic, block-compressed encoding (HF serves only v3), the
     embedded material equals the file name, `plane_size` equals the index size
     (the reader's own identity check, reached by opening the table through the
     bindings), `generator_version` parseable and not newer than the installed
     `helpmate`.
   - **V3 block integrity** — `verify_corpus.check_table`, reused as a function.
   - **V4 sidecar** — stream-decode all four planes block by block (numpy
     `bincount` per block), recompute invalid/unsolvable cell counts, the DTM
     histogram per side to move, and `max_dtm`; compare with the sidecar and the
     header. Must equal exactly.
   - **V5 deepest** — every FEN in the sidecar's `deepest` / `deepest_unique`
     probes to `max_dtm`.
   - **V6 local consistency** — for N random legal positions per side to move
     (default 2000 each, seeded, seed in the report) plus every V5 position: the
     table's DTM and count satisfy the recurrence the generator solves
     (`oracle.h`: plies to "Black is checkmated" with both sides cooperating;
     count = distinct optimal lines, saturating at 255): a mate reads 0 with
     count 1; otherwise dtm = 1 + min over legal successors, count =
     min(255, Σ counts of the minimising successors); unsolvable iff every
     successor is. Successors after captures and promotions are probed in the
     published sub-tables through the overlay. This catches wrong values
     without regenerating anything, because a corrupt table has to be corrupt
     consistently with its neighbours *and* with independently published
     sub-tables to pass.
   - **V7 independent oracle** — for up to 200 sampled positions with dtm ≤ 5
     plies, a python-chess iterative-deepening helpmate search (shares no code
     with the generator) must reproduce dtm and count.
4. *Report* — markdown with a per-check table, the sample seed, the PR head sha,
   and tool version, saved to `~/tb-staging/pr-N/report.md`. Unless `--no-post`,
   posted as a comment on the HF PR and on the linked claim issue. On failure the
   comment says what failed and asks for a fixed push to the same PR; nothing is
   closed.

Cost on a pawnless six-piece table (~2 GiB compressed, 29 GiB raw): download at
the box's rate, V3+V4 a few minutes, V6/V7 minutes. Pawn tables scale with raw
size (up to 85 GiB decoded, streamed — memory stays at one block).

**`contrib accept PR [PR ...] [--contributor LOGIN]`**

Preconditions: each PR has a passing report whose head sha equals the PR's
current head (a push after verification forces re-verification). Steps, each
idempotent so a rerun resumes after a failure:

1. Resolve the contributor: `GitHub: @` line in the PR description → the claim
   issue's author → the `contributors` map by HF username → `--contributor`
   (required on first sight of an unknown HF user; recorded afterwards).
2. Merge the HF PR(s) (`HfApi.merge_pull_request`).
3. Regenerate `manifest.json` from the HF repository's metadata
   (`list_repo_tree(expand=True)` gives LFS sha256 and size; small non-LFS
   sidecars are fetched and hashed), push it, and upload the regenerated
   `docs/hf-dataset-card.md` as `README.md`.
4. Move the verified files from staging into the local corpus.
5. On a branch `data/accept-<materials>`: update `contributions.json`, run
   `contrib sync` (below), add the CHANGELOG `### Data` entry, commit with a
   `Co-authored-by: <login> <id+login@users.noreply.github.com>` trailer (id from
   `gh api users/<login>`; omitted for anonymous contributors), open the PR,
   wait for the required checks, squash-merge, delete the branch.
6. Comment on the claim issue (materials accepted, link to the merged commit);
   close it when every material it claims is `done`. HF PRs close on merge.

A batch (`accept 2 3 … 15`) produces one HF merge per PR, one manifest push, and
one GitHub PR.

**`contrib sync`** — regenerate every derived text from `materials.universe()`,
the HF manifest, open HF PRs, open claim issues, and `contributions.json`:

- `docs/MATERIALS.md` — all 1000 materials. 3–5 pieces as compact grids per
  piece count (all done); six pieces as one table per White material
  (`KQ`, `KRR`, …) with columns *material · pawns · RAM tier · status ·
  contributor · HF PR*, and a summary header (done / in review / claimed / open /
  markers). Claimed/in-review reflect the moment `sync` ran; the claim issues'
  bot comments are the live view.
- The contributor tables in README.md and docs/hf-dataset-card.md, and
  `.all-contributorsrc`.
- The corpus numbers now edited by hand (six-piece done/outstanding, the missing-
  by-pawns tier table, file count, GiB, deepest mate) become generated spans:
  `<!-- contrib:six-done -->31<!-- /contrib -->`. `sync` rewrites the span
  contents only; prose stays hand-written.

### 6. Documentation changes

- CONTRIBUTING-TABLES.md: steps become "open a claim with the form → generate →
  `push --create-pr --claim N --github LOGIN` → you get a verification report on
  the PR". The "What gets checked" section is rewritten to describe V1–V7 and
  to state plainly what is still not proven (full correctness without
  regeneration; the C++ oracle is still future work).
- A short maintainer section (in docs/CONTRIBUTING-TABLES.md, at the end):
  `status` → `verify` → read the report → `accept`, and when to run the DEEPEST
  refresh.

## Error handling

- Network failures: every step reports which step failed and how to resume;
  `accept` records completed steps in `~/tb-staging/pr-N/state.json`.
- A PR that changes after verification: `accept` refuses, names both shas.
- Unknown contributor identity: `accept` stops before merging and asks for
  `--contributor`.
- Merge conflict on the docs PR (two batches accepted concurrently): `accept`
  rebases and re-runs `sync` before retrying once, then stops.

## Testing

- Unit: universe counts (1000; 70 six-piece markers; 645 real), canonicalisation
  and wildcard expansion, the claim parser against the text of issues #39, #40,
  #41, #45, status precedence, the span rewriter, report rendering, manifest
  from metadata, contributor resolution order.
- Verification against real tables: generate small tables in a fixture (3–4
  pieces, seconds), then **break what each check guards and watch it fail**:
  flip a byte inside a compressed frame (V3), recompress a table with one DTM
  cell altered (V4 and V6), edit the sidecar histogram (V4), rename a file to
  another material (V2), a count off by one (V6), a wrong shallow value (V7).
  Each mutation must fail exactly the checks meant to catch it.
- Commands against fake HF / GitHub clients: verify posts on pass and fail;
  accept resumes after a failure at each step; batch accept makes one GitHub PR.
- Workflow: `contrib_claims.py` tested with recorded GitHub/HF JSON; the YAML
  checked with actionlint.
- Coverage ≥ 80 % on the new Python modules; ruff and mypy as in CI.

## Rollout

1. Land components 1–6 (verify first: it is useful immediately).
2. First live run: `verify 2 … 15` on popeye37's KRR tables → `accept`.
3. `contrib sync` also closes any open claim issue whose materials are all
   `done`, with a comment — that closes #41 (T31M's KRB set, seeded record).
4. The open claims (#39, #40, #45) need no conversion — the parser reads them;
   the bot comment appears on the next run. The maintainer strikes KRRvkpp in
   #39 and T31M claims it in a new issue.

## Out of scope

- Automatic merge on a passing verification (declined).
- HF webhooks or a self-hosted runner.
- Exposing the C++ oracle as `helpmate verify` (still the best future check;
  V6/V7 are the Python stand-ins).
- Automatic DEEPEST / site / booklet refresh.
- Regenerating contributed tables to prove byte-identity (documented as a
  contribution anyone can make).
